## 3. Files Changed — Complete Record

### 3.1 New GPU monitor — `server/microcaption/monitor/gpu.py`

A `GpuMonitor` class that polls `nvidia-smi` in a **background thread** (default
1 s cadence) and caches the latest snapshot, so the HTTP metrics handler reads a
dict in memory rather than spawning a subprocess per request.

- One `nvidia-smi --query-gpu=… --format=csv,noheader,nounits` call per tick
  pulls: index, name, GPU util %, mem util %, VRAM used/total (MiB), temperature
  (°C), power draw/limit (W), fan %, SM clock, and mem clock.
- Derived fields computed server-side: `mem_pct` and `power_pct`.
- **Graceful degradation:** if `nvidia-smi` is absent or errors, the snapshot is
  `{available: false, reason: …}` — the server still runs fine on CPU-only / CI
  hosts.

**Why `nvidia-smi` and not `pynvml`/NVML bindings:** `pynvml` is not installed in
the venv, and Python 3.14 wheel availability is unreliable for this stack (same
constraint that blocks Parakeet/`nemo_toolkit`). Shelling out to `nvidia-smi`
adds zero dependencies and is robust.

```python
class GpuMonitor:
    def __init__(self, interval: float = 1.0) -> None: ...
    def start(self) -> None: ...          # no-op if nvidia-smi missing
    def stop(self) -> None: ...
    def snapshot(self) -> Dict: ...       # thread-safe copy of latest sample
```

### 3.3 Wire-up — `server/main.py`

- Instantiate and start the monitor at boot (interval overridable via

### 3.5 Monitor page rebuild — `client/monitor.html`

Replaced the two-card layout with a richer dashboard (page-specific styles kept
in an inline `<style>` block so other pages are untouched):

- **System summary row** (4 cards): active streams (with `N live / M total`
  sub-line), total cues, ASR backend + throughput, and GPU name + SM clock.
- **GPU section** (hidden + replaced by an "unavailable" note when
  `gpu.available` is false):
  - Four stat cards — Utilization, Memory (used / total GB), Temperature, Power
    (draw / limit) — each with a horizontal **gauge bar** that ramps
    green → amber → red (≥65% amber, ≥85% red; temp ramp 30–90 °C).
  - Four **canvas time-series charts**: GPU util %, VRAM used, temperature, power
    draw.
- **ASR performance section:** mean / p95 / max latency and throughput cards,
  plus two charts — inference latency (mean **and** p95 overlaid) and throughput
  (infer/s vs. concurrent **streams** overlaid). The streams overlay is the key
  stress-test signal: watch latency/util as the stream count climbs.
- **Sessions table** retained (now using the shared `.btn-watch` style).

**Charting:** a small inline `drawChart()` canvas renderer (no build step, in
keeping with the vanilla client). It is `devicePixelRatio`-aware, right-aligns
the newest sample, supports multiple series + an optional fill, and auto-scales
y unless a fixed `min`/`max` is given. History is kept client-side in ring
buffers (`HISTORY = 150` samples ≈ 5 min at the 2 s refresh cadence). On a failed
fetch the loop keeps the last good frame rather than blanking.

## 6. Open Items / Notes

- **Single-GPU UI:** the page renders `gpus[0]` only. The API already returns all
  GPUs; a per-GPU breakdown for multi-GPU hosts is a small follow-up.
- **Fan / clocks** are collected and exposed by the API but not yet surfaced as
  cards/charts on the page.
- **History is client-side only** — charts reset on page reload and span ~5 min.
  Longer-horizon stress runs would want server-side time-series retention.
- During stress testing, the chart to watch is **throughput (infer/s) vs.
  streams** alongside **GPU util** — the point where latency p95 rises while util
  saturates marks the concurrency ceiling (CLAUDE.md estimates ~6 streams at
  int8 / 1.0 s step on this card).
