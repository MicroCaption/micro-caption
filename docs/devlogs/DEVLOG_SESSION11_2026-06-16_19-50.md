## 3. Reality Check — what the live card actually does

Three behaviours only visible on real hardware, each of which broke an assumption
baked into the Session 10 (HW-untested) code:

1. **`decklinkvideosrc` is a live source.** It never posts `ASYNC_DONE` and never
   negotiates caps in `PAUSED` — so any "preroll to detect lock" logic hangs and
   reports nothing. The card exposes a read-only **`signal`** boolean ("True if
   there is a valid input signal available"); that, read in `PLAYING`, is the
   correct lock test. Mode comes from the negotiated caps once in `PLAYING`.

2. **No signal does *not* raise.** With no cable the card still streams **filler
   video + silent audio buffers** and only logs a `WARNING` ("Signal lost") — no
   `no-signal` *element* message. So a no-signal SDI session looks "live" forever
   and silently produces nothing.

3. **Duplex profile pairs the connectors.** Under the current profile, sub-devices
   **0,1 open as inputs** (signal=False, no cable) while **2,3 error as inputs**
   ("Internal data stream error") — they're the **output halves**. Emitting a test
   pattern on an output sub-device also errors until `profile` is set explicitly.
   This is the crux of Stage 3.

## 4. What Was Fixed (committed `c6355d2`)

| Area | Change |
|---|---|
| **Signal-status probe** | `decklink_devices._probe_signal` rewritten: run `decklinkvideosrc` in `PLAYING`, read the `signal` flag (+ caps mode) instead of waiting for `ASYNC_DONE` (which never came → it always returned `None`). |
| **No-signal watchdog** | `DeckLinkAdapter` now runs a watchdog thread that polls `signal`; if not locked within `io.decklink.signal_timeout_ms` (default **6000**), or signal is lost mid-stream, it ends the session with reason `error` instead of running silently. New config key in `settings.yaml`. |
| **Probe contention** | `_sdi_devices` no longer re-opens a sub-device a live session already holds — it reports `signal_locked=True` for in-use devices (double-open would contend with the capture). |
| **Label polish** | Strip GStreamer's `" (Video Capture)"`/`"(Audio Capture)"`/… suffix from picker labels → just "DeckLink Duo (1)". |

### Step B — verify Stage 2 end-to-end (real captions)
- Dashboard → **SDI** source → pick the locked sub-device → Start.
- Confirm **real captions** appear in the player (live ASR — never `--mock-asr`).
- Sanity-check audio: SDI embedded audio is what feeds ASR; if captions are empty
  but `signal_locked:true`, check the audio is actually present on the SDI embedded
  channels (silent program = no captions, correctly).

### Step C — build Stage 3 (SDI out + CEA-708 VANC)
1. **Set the duplex profile first.** Add a `profile` write to the output pipeline
   (e.g. `two-sub-devices-full` / `one-sub-device-full` per
   `io.decklink.profile`) so a connector pair can run **in + out simultaneously**.
   Today an unconfigured output sub-device errors with "Internal data stream error"
   — expect to resolve this before anything else in Stage 3 works.
2. **Pass video through, delayed.** Take the input video (don't drop it to
   `fakesink` as Stage 2 does) and delay it by `io.decklink.caption_delay_ms`
   (~3 s) to align with caption latency, then send to `decklinkvideosink`.
3. **Embed captions.** Bridge ASR output into GStreamer CC: reuse
   `DTVCC708Packetizer` → `appsrc` (`closedcaption/x-cea-708`) →
   `ccconverter` (format/framerate adapt) → `cccombiner` →
   `decklinkvideosink cc-line=<N>` (VANC insert). All elements confirmed present
   on this box (Session 10).
4. **Validate via the loopback** (Step A): capture the output on a second input and
   decode with `ccextractor` / a Line-21/708 decoder; confirm caption text + timing.

### Open implementation notes for Stage 3
- `InputOutputManager` is currently **audio-in only**; Stage 3 needs a video plane
  and an output sink — likely a new `DeckLinkOutputAdapter` or an extension of
  `DeckLinkAdapter` that keeps the video pad alive instead of draining it.
- Caption packets today flow only to `PacketLogger`/WebVTT — wiring them into an
  `appsrc` is the new path.
- The `cc-line` value and exact 708 service/framerate mapping will need tuning
  against the real signal mode (e.g. 1080i59.94 vs the 720x486 NTSC filler).
