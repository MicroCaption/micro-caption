## 3. Files Changed — Complete Record

### 3.1 Dashboard: rogue "Loading…" placeholder — `client/js/dashboard.js`

**Problem:** `dashboard.html` seeds the grid with
`<div class="empty-state">Loading…</div>`. On the first poll with active
sessions, `refresh()` found the existing `.sessions-grid` and *reused* it
without clearing it — so session cards were appended **after** the "Loading…"
node, leaving it stuck before the first card.

**Fix:** Remove the leftover placeholder once data arrives:

```js
let grid = wrap.querySelector('.sessions-grid');
if (!grid) { /* …create… */ }
const placeholder = grid.querySelector('.empty-state');
if (placeholder) placeholder.remove();
```

### 3.2 Graceful end-of-stream — server + client

When a source reached GStreamer EOS, the adapter stopped itself but nothing told
the `Session`, so it stayed `status: 'live'` on the dashboard indefinitely.

**`server/microcaption/io/base.py`** — added an end-callback hook to the adapter
base class:

```python
EndCallback = Callable[[str], None]   # reason → None ('eos' | 'error')
def set_end_callback(self, callback): self._end_callback = callback
```

**`server/microcaption/io/youtube_adapter.py`**
- New `_notify_end(reason)` fires the callback **once**, on a separate thread
  (off the GLib loop thread).
- `_on_eos` → `_notify_end('eos')`; `_on_bus_error` → `_notify_end('error')`.
- Fixed a latent bug: `stop()` called `self._thread.join()` even when invoked
  from the GLib loop thread itself (EOS/error handlers run there), which raises
  *"cannot join current thread."* Now guarded with
  `if self._thread is not threading.current_thread()`.

**`server/main.py`** — `_on_source_end(reason)` marks the session `ended` (new
status), keeps it **registered so its caption log stays viewable**, and stops
the ASR pipeline to release the shared GPU worker. The `_launch` thread now
guards `if sess.status != 'ended'` before setting `'live'` (fast-EOS race).

**`server/microcaption/session.py`** — documented the new `'ended'` status.

**Client (`dashboard.js`, `shared.css`):** ended cards render greyed/dimmed with
an `ENDED` tag, a **Caption log** link (opens the player in replay mode), and a
**Remove** button. Because a card's action buttons differ by state, `_updateCard`
now re-renders the whole card when `status` changes (tracked via
`card.dataset.status`).

**Client (`watch.js`):** the caption-only viewer's reconnect poll now treats a
`status: 'ended'` response (not just a 404) as "Stream ended".

**Verified live:** a real stream (`SJSv7AaiByM`) hit EOS during testing → tagged
`ended`, all 67 cues retained and retrievable via
`/api/session/<id>/cues`, and `/api/watch/<code>` returned `ended`.

### 3.3 Caption-only viewer buffering — `client/js/watch.js`

The caption-only viewer already used the shared `CaptionPacer`, but it collapsed
each block's dwell to ~1.2s when behind live (the "word-by-word" churn). With no
video to stay in lock-step with, the viewer now favours readability:

```js
new CaptionPacer(renderLines, {
  minDwell: 3000,   // hold each ≤2×32 block ≥3s
  maxDwell: 6000,
  maxLagSec: 6.0,   // tolerate lag rather than churn text
  maxBacklog: 4,
  idleClearMs: 8000,
});
```

Full blocks appear at once and hold for a comfortable minimum of 3 seconds.

### 3.4 Caption-log replay showed no captions — `client/js/player.js`

**Root cause:** `replayTick()` guarded on `window.ytPlayer`, but `ytPlayer` is a
top-level `let` — `let`/`const` bindings are **not** properties of `window`
(only `var`/globals are). So `window.ytPlayer` was always `undefined` and the
function returned on every tick, never rendering a cue. The video played; the
captions never did.

**Fix:** guard on the binding itself:

```js
if (!ytPlayer || typeof ytPlayer.getCurrentTime !== 'function') return;
```

Cues are fetched fine, so historical captions now replay in sync with the
video's current time.

### 3.5 Fullscreen drops captions — `client/player.html`

**The constraint:** the video plays in a **cross-origin** `<iframe>`
(youtube.com). Two hard browser rules apply:
- **Fullscreen API:** only the fullscreen element's subtree renders. YouTube's
  own fullscreen button fullscreens *the iframe*, and we cannot inject our
  caption overlay into a cross-origin iframe's document.
- **Canvas compositing is impossible:** you can't read pixels from a cross-origin
  iframe/video (`drawImage` taints/throws), and YouTube exposes no CORS-enabled
  video element — so we can't paint "video + captions" to our own canvas.

**The only robust path is to own the fullscreen control.** Implementation:
- `fs=0` on the embed URL disables YouTube's native fullscreen button (it would
  bypass our overlay).
- A custom fullscreen control fullscreens the whole `#player-wrap` wrapper
  (iframe **and** caption overlay together), so captions always ride along.
- The control is presented as an **on-video button** (bottom-right, hover-reveal,
  `#fs-overlay-btn`) where users expect it, plus a labeled toolbar button. Since
  YouTube's own button is gone, every fullscreen path now goes through ours.
- Fullscreen CSS: iframe fills the screen, the caption bar stays anchored bottom,
  and caption text scales to 2em for distance reading.

**Note for the future:** if a source is ever switched to a same-origin player or
a raw `<video>` element, the canvas/true-overlay options reopen.

### 3.6 Toolbar alignment + site-wide button standardization

**Alignment bug:** the "From beginning" / "Jump to live" control sat in a
`<span>` wrapper and was a different element type (`<a>` vs `<button>`) with a
different box model than its toolbar neighbours, so it rendered at a different
height.

**`client/css/shared.css` — one button system.** `.btn-primary` (filled CTA),
`.btn-watch` (green outline), `.btn-neutral` (grey outline — new), and
`.btn-danger` (red outline) now share a single box model: `inline-flex`,
vertically centered, identical `line-height`, padding, and font-size — so
`<a>` links and `<button>`s line up identically wherever they sit together. The
compact card `.btn-stop` was modernized to `inline-flex` too.

**`client/player.html`** was the **only** page not using `shared.css` — it
carried its own inline button styles (the source of both the misalignment and
the inconsistency). It now links `shared.css`, uses the shared button classes in
its toolbar, and keeps only player-specific layout inline. Alignment fixes:
- `#topbar-actions { display:flex; align-items:center }`
- `#mode-btn-wrap { display:contents }` so the dynamically-swapped mode button
  becomes a direct flex item and lines up with its siblings.

**Left intentionally distinct:** the landing pages (index/pricing/standards/
watch via `landing.css`) and the caption-only viewer (`viewer.css`).
