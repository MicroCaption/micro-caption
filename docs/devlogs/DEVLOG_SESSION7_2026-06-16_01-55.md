## 2. Diagnosis — Why the GPU "Spikes"

The ASR pipeline is **bursty by design**, and a single real-time stream makes it
obvious (`server/microcaption/asr/pipeline.py`, growing-buffer LocalAgreement
loop):

- The worker waits for `step_duration` (currently **0.7 s**) of *new* audio to
  accumulate. Because the source is real-time, that is ~0.7 wall-clock seconds
  of the GPU doing essentially nothing.
- It then fires **one** Whisper inference on the buffer
  (`_primary.transcribe_words(buf)`), measured at ~100 ms mean latency.
- Then back to idle until the next step.

So the GPU does roughly **100 ms of work every 700 ms ≈ 14 % duty cycle**. The
*instantaneous* spikes are tall (a `large-v3-turbo` / `float16` inference is
heavy) but *average* load is low — exactly the healthy pattern the "~6 concurrent
streams" estimate in `CLAUDE.md` is built on.

Two things exaggerated the visual spikiness:

1. **Sampling artifact.** `nvidia-smi`'s `utilization.gpu` is "% of the sample
   window a kernel ran." We polled it every 1 s and the page redrew every 2 s, so
   a 100 ms burst landed randomly inside the window → jumpy 0 % / 70 % readings.
2. **Growing buffer.** The buffer grows until a commit trims it (up to
   `max_buffer_duration: 14 s`), so per-burst cost — and therefore spike height —
   varies.

**Conclusion:** for one stream this is **not a problem** — average utilization is
low and latency (~100 ms) is well under the 700 ms budget. The right move was to
make the *chart* represent duty cycle rather than sampling noise, not to change
the inference engine. (Engine knobs — `compute_type: int8`, larger
`step_duration`, smaller model — were discussed as Option B for actually lowering
spike height when chasing multi-stream headroom, but deferred.)

## 3. Files Changed — Complete Record (Option A)

### 3.1 Faster polling + rolling average — `server/microcaption/monitor/gpu.py`

- Default poll `interval` lowered **1.0 s → 0.25 s** (fast enough to sample the
  burst structure).
- New `avg_window_s` (default **5.0 s**) → the monitor keeps a per-GPU rolling
  window of recent samples (`util` and `power`) and computes a smoothed mean.
- A new static `_roll()` helper appends a sample and returns the window mean.
- Each GPU snapshot now carries the spiky instantaneous values **plus** smoothed
  companions:
  - `util_gpu_avg`
  - `power_w_avg`, `power_pct_avg`
  - `avg_window_s` (so the client can label the window)

The rolling average is computed **server-side on purpose**: the page only reads
one snapshot per 2 s refresh, so the duty-cycle average must be accumulated
across the fast samples on the server, not in the browser.

### 3.2 Config knobs — `server/main.py` + `server/config/settings.yaml`

- `main.py` constructs `GpuMonitor(interval=monitor.gpu_interval,
  avg_window_s=monitor.gpu_avg_window)`.
- `settings.yaml` `monitor:` block gains:

  ```yaml
  gpu_interval: 0.25    # nvidia-smi poll cadence (s); fast enough to catch ASR bursts
  gpu_avg_window: 5.0   # rolling window (s) for the smoothed GPU duty-cycle average
  ```

  Both overridable via `MC_*` env vars like any nested key.

### 3.3 Chart overlay — `client/monitor.html`

- GPU **utilization** and **power** charts now draw two series: a **faint
  instantaneous line** (the spikes, thin + light fill) under a **bold
  rolling-average line** (the duty cycle). Added an `inst / avg` legend to both
  chart headers.
- Stat cards and gauge bars now read the **average** (`util_gpu_avg` /
  `power_w_avg` / `power_pct_avg`), so the headline numbers are stable and
  meaningful instead of jittering; the chart-value labels are suffixed
  `% avg` / `W avg`.
- Falls back to instantaneous values (`?? util`) if the server build predates the
  avg fields.

## 5. Incident Note — Server Restart Churn

Loading the new GPU wiring required a server restart. Background launches via the
Bash tool's shell `&` did **not** persist (the job is torn down when the tool
call returns), which led to several failed restart attempts. During that churn
the running server instance — which had been processing live sessions (a Twitch
stream and a YouTube video) — was killed.

**Resolution:** the server was brought back up cleanly via a harness-tracked
background process and is healthy but **idle**; the previously-running sessions
were lost and must be resubmitted.

**Lesson for next time:**
- Start long-lived processes with the harness-tracked background mode, not shell
  `&`.
- Check whether a running server is actively serving the user's sessions *before*
  killing it to reload code.
